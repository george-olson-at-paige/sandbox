# API needs: what the UI work has found

One ledger of every API change the `@paige/ui` spike has found so far (REVIEW-13 R13-01), so the API side can do them together. **Nothing in the API changes this round**: this lists the work, it doesn't do it.

How to use it: one row per change, grouped by area. Each row says what the UI needs, the shape the UI expects (TypeScript, matching the types the UI already exports), the spike file that consumes it, where it was found (GAPS # or R-id), and a status:

- **needed**: the UI is built against a fixture or stand-in and waits on this.
- **keep**: the API already does this and the UI depends on it; don't change it.
- **to confirm**: a likely shape; confirm with George or Product before building (the Partners rows say which open question in REVIEW-13 R13-22 they wait on).
- **Product first**: Product decides what it means before anyone builds it.

Paths are relative to `spikes/paige-ui-test-pass/`. "admin-site" means the `feature/admin-site` branch (not yet in develop), where the admin's `Admin/People`, `Admin/Jobs`, `Admin/Billing` and `Admin/Reporting` slices live; "develop" means this branch's `src/api/application/Paige.Application`. Every failure in every row returns the error shape in A1.

## Notes

- **Search is never in a URL.** A typed email is PII, and product-engineering rule 7 keeps PII out of URLs (ingress and analytics log them). The web keeps the search per tab and out of the address bar. Recommendation: the list endpoints are `POST admin/people/query` and `POST admin/partners/query` with the whole state in the body, rather than `GET admin/people?q=…`. The same goes for A8.
- **The reason is required and audited** on every support action (A22–A26, A36's deactivate; optional on a logo upload, A31): 400 `reason_required` when blank, as admin-site's actions already do, and the operator action records it.
- **Bulk by query** (A22): the API resolves the query when the request arrives and acts on that set. A person who stops matching (already verified, already disabled) is skipped and counted, never failed. The web clears the selection after any bulk action.
- **Types follow the UI's exports** (R13-02): `PersonRow`, `PlanKind`, `PersonStatus`, `ListState`, `AdminMetric`, `PipelineRun`, `RichTextValue`. When the API's generated types match them, screens connect them with `satisfies` and need no mapper. If a wire name differs, there is one typed adapter per feature, next to its screen.
